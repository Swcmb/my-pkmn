## 四、第一阶段：备份并替换原卡牌库

### 4.1 定位原卡牌库

搜索项目中所有卡牌数据库及其读取位置。

检查：

- `cards.csv`、`*cards*.csv` 等可能的数据文件。
- `rl/encoding.py`。
- `rl/policy.py`。
- `rl/decks.py`。
- `scripts/` 下的牌组生成、卡牌检查和提交导出代码。
- `sdk_cg/` 与提交包中所有读取卡牌元数据的代码。
- 项目内可能由原始 CSV 生成的 JSON、索引、缓存和映射文件。

确定唯一的权威卡牌库路径，并明确区分原始卡牌数据、派生数据与引擎内部卡牌库。

不能把 `agent/deck.csv` 当作卡牌数据库；它是提交牌组。

### 4.2 备份原数据库

在新的迁移目录中保存原数据库的完整副本。例如：

`runs\card_database_migration\20261020\original_cards.csv`

如果目录已存在，使用新的唯一目录。

覆盖之前计算原文件 SHA-256，并确保备份文件与原文件哈希一致。

### 4.3 校验新卡牌库

从本地读取：

`E:\Files\Downloads\cards.csv`

首先确认文件存在、可读取、非空。将其复制到新的迁移临时文件：

`runs\card_database_migration\20261020\downloaded_cards.csv`

使用 Python 标准库 `csv` 或项目既有解析逻辑读取。

检查：

- 编码和 CSV 格式。
- 列名、列顺序及必要字段。
- 数据行数。
- 卡牌 ID 是否存在空值或重复值。
- 必要字段是否有异常类型或无法解析的内容。
- 卡牌名称、类型、进化关系、招式、特性和能量需求的格式。
- 是否存在误将表头、错误页面或其他非卡牌记录当作卡牌行的情况。

不要假定新文件仍然只有 1267 张卡牌。以新 CSV 中通过验证的真实记录为准。

### 4.4 比较旧、新卡牌库

生成旧、新卡牌的比较结果，至少包含：

- 新增和删除的卡牌 ID。
- 新旧均存在的卡牌 ID。
- 相同 ID 的名称是否变化。
- `cardType`、`pokemonType`、`basic`、进化关系等字段的变化。
- HP、招式 ID、招式伤害、能量需求和 `skills` 的变化。
- 新增字段、缺失字段及字段语义变化。
- 新旧卡牌 ID 映射是否保持一致。

将结果保存到：

`runs\card_database_migration\20261020\schema_comparison.json`

同时生成：

`runs\card_database_migration\20261020\id_mapping_comparison.json`

如有需要，补充便于阅读的 Markdown 报告。

### 4.5 覆盖原数据库

只有完成备份、格式校验及 schema 检查后，才执行覆盖。

将 `downloaded_cards.csv` 复制并覆盖项目中定位到的原始权威卡牌库文件。优先使用同卷临时文件和原子替换，防止覆盖过程中留下损坏文件。

覆盖后重新计算 SHA-256，必须与新源文件一致。

如果校验失败，保留原数据库，不得使用错误数据覆盖。

完成后明确记录：

- 原数据库绝对路径。
- 原数据库 SHA-256。
- 备份路径和哈希。
- 新数据库路径。
- 新数据库 SHA-256。
- 实际记录数。
- 新旧 ID 与语义差异。

不要为了迁移而直接覆盖所有派生 JSON、模型权重或牌组文件。它们必须在分析其依赖关系后分别处理。

## 五、第二阶段：验证数据库解析与模型兼容性

### 5.1 验证卡牌解析

重新运行项目原有的卡牌数据读取入口，例如 `all_card_data()` 和相关索引构造函数。

检查：

- CSV 可以完整解析。
- 卡牌 ID 查询正确。
- 名称与属性映射正确。
- 招式与技能能够解析。
- 不存在索引越界、重复映射或关键字段缺失。
- 牌组工具、训练入口与 Agent 编码器能够读取新数据。

优先复用已有测试，只添加解决本次迁移所需的最少测试。

### 5.2 验证现有 checkpoint

首先检查：

`runs\train-20m-e16-1m\ckpt_999424.pt`

以及：

`runs\train-20m-e16-1m\ckpt_500736.pt`

重点检查：

- `net_config`。
- 模型输入维度。
- 卡牌 token / embedding 的映射。
- 卡牌属性编码。
- `would_ko` 特征。
- `model.pt` 的导出方式。
- 训练时使用的数据文件与当前数据文件的语义差异。

判定原则：

- 若模型输入表示的是卡牌稳定语义，且相关字段与 ID 映射一致，可以继续测试旧 checkpoint。
- 若 ID 被重新分配，但模型将 ID 直接当作类别或索引，则必须检查权重与映射能否兼容。
- 若卡牌顺序、embedding 或输入语义发生变化，必须明确风险。
- 即使模型成功加载，也需要通过输入、推理和对战回归测试才能确认兼容。
- 如果无法证明 checkpoint 与新数据库兼容，保留旧模型，不得继续微调或将其导出为有效候选提交包。

**数据库更新不等于模型自动适配。**

### 6.1 重建 Dragapult 候选

使用新卡牌库核对旧 Dragapult 牌组：

- 不依据旧卡牌 ID 直接认定新 ID 仍对应相同卡牌。
- 同名多印刷版本必须根据实际语义、招式与进化关系确认。
- 所有牌组中的 ID 均须能从新卡牌库找到。
- 若旧牌组无法完整映射，重新构建候选并说明原因。

### 6.2 牌组合法性验证

每副候选牌组必须满足：

- 恰好 60 张卡牌。
- 所有 ID 存在于新卡牌库。
- 满足同名卡数量限制。
- 满足 ACE SPEC 数量限制。
- 至少包含 1 张引擎真正认可的基础宝可梦。
- 进化关系正确。
- 所有卡牌均被当前 CABT 引擎支持。

不能仅依赖 Python 对 CSV 的检查。必须使用实际 CABT 引擎执行开局校验，确保引擎接受牌组。

### 6.3 重新评估候选牌组

保持模型 checkpoint、推理策略、编码路径和环境参数一致，仅改变牌组。

评估至少包含：

1. 新 Dragapult 候选。
2. 当前 `agent/deck.csv`，前提是它能在新库中验证。
3. 至少一副合法的补充候选牌组（如可构建）。

使用两个独立种子开展双向交叉评估，严格平衡座位。

记录：

- 胜率与 Wilson 95% 置信区间。
- 分座位胜率。
- 平局、异常与非法动作。
- 平均对局长度及耗时。
- 每副牌组的 SHA-256。
- 新旧卡牌库版本与映射差异。

不得直接沿用旧牌组评估结果作为新数据库上的最终结论。

输出：

`runs\evaluation\card_database_migration\deck_validation_report.md`
