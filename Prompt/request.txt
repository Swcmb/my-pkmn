# 任务：开发 PTCG-Arena 平台自动化工具

## 1. 项目目标

在 `D:\pkmn-kaggle` 项目之外建立独立工具，帮助我操作：

- 平台：`http://115.159.47.81/`
- 用户名：从本地环境变量或安全凭证文件读取
- 密码：从本地环境变量或安全凭证文件读取
- 本地比赛项目：`D:\pkmn-kaggle`
- Python：`D:\ProgramFiles\deeplearning\python.exe`

工具名称：`ptcg-arena-cli`

目标交付物：

1. Python CLI，负责实际执行平台操作。
2. Claude Code Skill，负责理解任务、编排 CLI、分析结果。
3. 自动化测试与使用文档。
4. 可选 MCP 适配层，仅在确实需要结构化工具调用时实现。

优先实现 CLI + Skill。不要一开始就同时开发三套重复的接口。

## 2. 开发原则

- 先检查项目目录、Git 状态、现有脚本和依赖。
- 先审计平台真实行为，再决定采用 HTTP API、网页表单或浏览器自动化。
- 不得臆造 API 路径、请求字段、认证方式、提交格式或排行榜接口。
- 只实现已验证的平台能力。
- 尽量复用现有代码和依赖，保持变更范围最小。
- 新增代码、文档和注释使用中文；命令、路径、API 字段和产品名称保持原样。
- 不覆盖、删除或迁移现有训练结果和模型文件。
- 不将密码、Cookie、Token、Session 或其他凭证写入日志、Git 或报告。
- 任何平台写操作都必须先确认实际影响。
- 训练由我本人运行；工具可以准备训练命令、监控结果和分析报告，但不能擅自启动训练。
- 模型导出可以由 AI 执行；执行前检查输入文件和目标路径，导出后验证产物。
- 提交正式 Agent、覆盖已提交版本、启动可能影响排名的正式比赛等操作，必须获得我的明确确认。

## 3. 阶段一：审计平台

首先检查首页、登录页面、页面静态资源、公开文档以及可合法访问的接口。

确认并记录：

1. 登录方式及认证生命周期。
2. 平台是否提供公开或登录后 API。
3. 比赛状态、当前榜单、赛程、轮次和历史结果的获取方式。
4. Agent 提交方式、文件格式、大小限制和校验规则。
5. 开发期 A 榜与正式 B 榜的区别。
6. 平台是否支持查询当前用户提交状态及已提交版本。
7. 是否有公开接口文档或管理员提供的接口说明。
8. 浏览器自动化是否为必要手段。

优先使用稳定的 HTTP API；没有可用 API 时，再考虑浏览器自动化。

禁止绕过认证、验证码、权限检查或访问控制。遇到未知行为时，记录请求和响应结构中的非敏感信息，不猜测接口。

输出：
`docs/platform-audit.md`

每项标记为：
- 已实测
- 根据页面或文档确认
- 尚未验证

如果当前无法登录或访问，先输出审计结果和缺失信息，继续实现不依赖平台连接的部分。

## 4. 阶段二：CLI 命令设计

设计统一命令入口：

`ptcg-arena`

建议命令：

### 平台连接

- `ptcg-arena status`
- `ptcg-arena auth login`
- `ptcg-arena auth status`
- `ptcg-arena auth logout`

登录交互中使用隐藏输入或安全凭证存储，不将密码写入命令行参数。

### 比赛信息

- `ptcg-arena competition status`
- `ptcg-arena leaderboard`
- `ptcg-arena rounds`
- `ptcg-arena results`

只有平台确实提供对应信息时才实现这些命令。每条命令必须明确区分真实数据、缓存数据与不可用状态。

### Agent 管理

- `ptcg-arena agent validate <submission.tar.gz>`
- `ptcg-arena agent inspect <submission.tar.gz>`
- `ptcg-arena agent submit <submission.tar.gz>`

提交命令必须在真正执行写操作前展示目标赛事、文件名、文件大小和校验结果，并要求显式确认。若平台不支持安全的重复提交检查，应在文档中说明。

### 运行记录

- `ptcg-arena history`
- `ptcg-arena report <run-id>`

使用本地 SQLite 或 JSONL 保存运行记录，默认仅保存必要的时间、操作、文件摘要、结果和非敏感错误信息。

## 5. 阶段三：本地 Agent 与模型集成

先检查 `D:\pkmn-kaggle` 的真实文件结构和现有导出脚本。

本地项目中已知的候选模型：

`runs\train-20m-e16-1m\ckpt_999424.pt`

已知导出配置：

- Backend：`transformer2`
- Deck：`runs\evaluation\card_database_migration\best_deck.csv`
- 输出：`submission_rl_transformer2_db_migrated.tar.gz`
- 构建目录：`submission_rl_transformer2_db_migrated`

生成导出命令时，使用项目实际存在的脚本、参数和文件。不要把这些路径视为未经检查就一定有效。

训练策略：

- 不启动训练。
- 不自动选择未经评估的检查点替换现有候选。
- 可以分析已有训练日志、评估报告和对战结果。
- 可以生成供我手动运行的训练命令。

导出策略：

- 检查检查点、牌组、脚本和 Python 环境是否存在。
- 导出前确认目标文件是否已存在。
- 需要覆盖时先征得我同意。
- 导出后检查 TAR 结构、`main.py`、`deck.csv`、牌组合法性及平台要求。
- 有可运行的本地测试时执行测试，并记录真实退出码。
- 结构性检查通过不代表平台已接受提交，必须区分这两种状态。

## 6. 阶段四：牌组与提交包验证

读取实际的 `cards.csv`、`deck.csv` 和导出实现，建立独立校验器。

按照平台实际规则检查：

- 提交包内必需文件。
- `deck.csv` 是否恰好包含 60 张有效卡牌 ID。
- 至少一张真正的基础宝可梦。
- 同名卡最多四张，基础能量按实际规则处理。
- ACE SPEC 最多一张。
- `main.py` 是否包含要求的 `agent(obs_dict)` 函数。
- 返回动作索引是否合法，数量是否满足 minCount 和 maxCount。
- 运行时间及异常行为是否满足平台限制。

以实际平台规则为准；任何尚未确认的规则必须明确标注。

编写无效牌组、缺少文件、非法动作及错误选择数量的测试。

## 7. 阶段五：Claude Code Skill

建立独立 Skill：

`.claude/skills/ptcg-arena/SKILL.md`

Skill 应说明：

1. 如何发现并调用 CLI。
2. 如何读取比赛状态、排名和历史结果。
3. 如何验证提交包。
4. 如何比较模型评估报告。
5. 如何准备导出命令。
6. 如何处理平台连接失败、登录失效及提交失败。
7. 哪些操作需要用户确认。
8. 如何生成中文 Markdown 报告。

Skill 必须使用实际存在的命令，不引用尚未实现的功能。

支持以下自然语言任务：

- 查看比赛当前状态。
- 查询我的平台提交记录。
- 检查指定提交包。
- 分析候选模型的实测结果。
- 准备模型导出。
- 导出并验证提交包。
- 比较不同模型的对战表现。
- 生成正式提交前的检查报告。

## 8. 阶段六：测试与验收

先完成不依赖平台连接的单元测试，再执行真实平台只读测试。

验收标准：

1. CLI 可以安装，并能显示帮助。
2. 未配置凭证时，程序不会泄露或伪造登录状态。
3. 无效提交包能够被拒绝，并给出明确原因。
4. 正常提交包能够完成本地结构检查。
5. 所有平台命令均有真实接口或页面依据。
6. 网络异常时返回可诊断错误，不将失败报告成成功。
7. 凭证不会进入 Git、普通日志和测试快照。
8. 未确认的正式写操作不会执行。
9. 训练不会自动启动。
10. Skill 的每个命令均可在实际 CLI 中找到对应实现。
11. 所有可运行的测试均实际执行，并记录结果。
12. 输出最终文件树、使用示例、测试结果和未完成事项。

## 9. 执行流程

按以下顺序工作：

1. 检查项目与平台。
2. 输出简短实施计划和关键不确定项。
3. 实现 CLI 最小可用版本。
4. 实现平台只读适配器。
5. 实现提交包校验。
6. 编写并验证 Skill。
7. 根据已确认的平台接口实现必要的写操作。
8. 运行测试并生成验收报告。

不要在审计阶段结束后只给建议；继续完成能够独立实现和验证的部分。

遇到必须由我提供的登录验证或必须由我确认的正式操作时，暂停该操作，继续完成其他不依赖它的工作。

最终输出：
- 新增及修改文件清单
- 安装和使用命令
- 已验证的平台功能
- 实际测试结果
- 尚未验证的能力
- 正式提交前的风险与检查清单
