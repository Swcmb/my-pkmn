## 目标

不启动新的长时间训练。先查明为什么候选模型对旧基线胜率为 62%，对随机合法策略胜率只有 43%，对同架构随机初始化模型胜率只有 22%；同时确定提交包的 `would_ko=True` 路径如何正确验证。

## 第一阶段：核对评估实现

1. 检查 `runs/evaluation/eval_h2h.py`、实际调用的对战 runner、策略封装和奖励计算。
2. 确认每局中候选、对手与 `seat0`、`seat1` 的对应关系，检查先后手处理是否与报告描述一致。
3. 检查 `random_legal` 是否确实从当前状态的合法动作中随机选择动作，排除动作索引、动作掩码、玩家状态或奖励归属错误。
4. 检查 `untrained_same_config` 是否使用了正确的网络结构、观测编码、动作空间、权重初始化和推理逻辑。
5. 检查 `mirror`、牌组轮换、随机种子及终局胜负统计，重点排除候选与对手之间不对称的环境或数据路径。
6. 核对 JSON 中的 `meta`、真实 checkpoint 路径、模型步数和策略标签。不要依赖已知不可靠的硬编码 `label` 字段。

## 第二阶段：进行最小化交叉验证

优先复用仓库现有评估代码，不要重写训练框架。

使用固定种子和相同牌组，尽可能对同一场景交换座位，至少覆盖以下对局：

- 候选模型 vs 旧基线。
- 候选模型 vs 随机合法策略。
- 候选模型 vs 同架构随机初始化策略。
- 旧基线 vs 随机合法策略。
- 旧基线 vs 同架构随机初始化策略。
- 候选模型 vs 自身的镜像对局。

每组先运行足够的小样本确认统计逻辑正确；若无异常，再运行至少 100 局并严格均衡座位。报告总胜率、分座位胜率、95% Wilson 置信区间、平局、异常、非法动作率、平均对局长度与实际耗时。

不要因为不同策略之间呈现非传递性就直接判定代码有错；必须结合实现检查和交叉对局证据给出结论。

## 第三阶段：修复或明确提交推理阻塞

1. 追踪 `main.py` 中 `would_ko=True` 对应的真实执行路径，确认具体哪些调用依赖 `WouldKO`、`GetSerialObs`、`GetBinaryObs`。
2. 检查仓库已有的 DLL、引擎及官方或比赛 SDK 资源，确定正确的验证方式。
3. 不允许为了通过本地测试而伪造 DLL 导出、静默跳过必需功能，或用 `native_encode=False` 的测试结果冒充 `native_encode=True` 的结果。
4. 不要直接关闭 `would_ko` 后宣称模型兼容；若提出关闭方案，必须先验证观测维度、输入分布及模型配置是否匹配。
5. 在可用环境内单独验证提交包入口、动作返回格式、牌组文件和推理完整路径。若真实平台环境不可获取，明确记录剩余阻塞和验证范围。

## 第四阶段：输出报告并做出决策

更新 `runs/evaluation/audit_report.md`，包含：

- 已确认问题、证据文件和相关代码位置。
- 评估实现是否正确，以及仍未确定的问题。
- 各对局的总胜率、分座位胜率和置信区间。
- 提交包实际验证通过的项目与阻塞项。
- 是否值得继续训练、应优先修复什么，以及支持该建议的实测证据。

本阶段禁止启动新的长时间训练，也禁止覆盖现有 checkpoint 和提交包。

成功标准：找到战绩异常的可信解释，获得可复现的交叉对局结果，并明确当前模型能否进入下一阶段验证。未经实测的结论必须标记为未验证。
