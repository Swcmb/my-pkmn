- 日期：2026-10-17 ~ 2026-10-18

## 口径声明

1. 唯一变量是 `--num-envs`（8 / 16 / 32）；`--decks sample`、`--num-steps 64`、`--num-minibatches 16`、`--log-every 1`、`--seed 1`、JSON 编码路径、torch.compile 关闭、原生编码关闭、teacher 与额外对手网络关闭全部固定。JSON 编码路径强制 `envs_per_worker=1`（`rl/env_selfplay.py`），因此并行环境数即采样进程数。
2. 本报告中的 `sps` 一律指训练日志单次迭代的环境步速率（分子 = `num_envs × num_steps`，全局环境步/s），不乘 `num_envs`，也不与采集/更新阶段的 samples/s 混同。
3. `e2e` 端到端环境步/s = `完成环境步数 / 实际运行时间`（含启动、模型初始化与检查点保存开销）。
4. E32 未正常完成（exit_code=1，CUDA OOM），其数值如实列出但标注为失败，且不用于完整训练工期外推。
5. 全部数值来自实际执行产物（`train.log` / `monitor.csv` / `run_meta.txt` / `summary.json`），无模拟数据；未测得项标注"未测得"。

## 结论速览

1. 推荐配置：**E16（`--num-envs 16`）**。稳定段 sps 均值 88.095 为三配置最高，exit_code=0，显存峰值 6163/8151 MiB（约 24.4% 余量），端到端 86.633 环境步/s。
2. E32 不可用：稳定段 sps 41.0，端到端 39.777；迭代更新耗时从 8.119 s（E16）膨胀到 44.286 s，并在第 31/40 次迭代处 CUDA OOM 退出，属于非平稳的显存退化路径，而非单纯并行收益。
3. 规模边界：以本次实测 e2e 速率外推，E16 跑 100M 环境步约 13.4 天连续；11B 环境步约 1,470 天连续，本机不可行。

### 与作者训练配置的对照

作者仓库仅说明使用约 20M 的 transformer / generalist 模型（`WRITEUP.md` L59-75、`README.md` L9-11），**精确网络配置未公开**。因此本报告网络只能标注为"约 20M 的本地候选配置"，不能宣称与作者完全一致。

作者公开训练配置与本机基准的成分差异：

- num_envs：作者 768 vs 本机 8 / 16 / 32（本基准唯一变量）
- batch：作者 196,608 vs 本机 512 / 1024 / 2048（= num_envs × num_steps）
- num_minibatches：作者 4 vs 本机 16
- lr：作者 1e-4 阶梯式下降 vs 本机 2.5e-4 cosine
- ent_coef：作者 0.002 vs 本机 0.01
- teacher / 预训练：作者 teacher_kl=0.005 + 预训练 vs 本机 teacher 关闭、无预训练
- 硬件：作者 4×H200（约 16.5k steps/s）vs 本机 RTX 5060 Laptop
- 牌池：作者 4,941 张 vs 本机 sample 子集
- 作者另有 gamma=0.997、gae=0.95、clip=0.2；本机对应值未逐项核对。

另外：`ff=256` 不生效——本地 `rl/policy.py`（L329）将前馈宽度固定为 `ff = 4 * d_model`（= 2176）。

口径说明：本报告的估算只依赖环境步吞吐（sps），配方差异不影响吞吐可比性；上述差异仅说明本基准是吞吐基准，而非作者训练设置的复刻。

## 5. 瓶颈诊断

逐问用实测数据回答：

1. **GPU 计算是否饱和**：稳定段 GPU 利用率均值 E8 75.46% / E16 84.79% / E32 96.77%；利用率 ≥90% 的采样占比 55.78% / 67.16% / 89.64%。E8/E16 未饱和（仍有余量），E32 接近饱和但以显存临界为代价。
2. **环境采样或 Python 编码是否耗时过高**：step 阶段（采样+JSON 编码+回传，原生编码关、`envs_per_worker=1`）每次迭代均值 0.2 / 0.4 / 0.467 s，占采集阶段约 9.5% / 11.6% / 9.4%。绝对值随并行数近线性增长，但占比低——不是瓶颈。
3. **模型前向与 PPO 更新占比**：按时间重算，collect 占迭代 34.96% / 29.75% / 10.12%，update 占 65.04% / 70.25% / 89.88%；采集阶段内 fwd（前向）占 90.49% / 88.64% / 90.54%。前向是采集阶段的绝对主导；更新阶段在 E16/E32 是整体主导。
4. **增加并行环境数是否提高整体吞吐量**：E8 82.667 → E16 88.095 sps（+6.6%）；E16 → E32 41.000 sps（−53.5%）。收益在 8→16 已很小，16→32 转为大幅负收益。
5. **是否出现显存、RAM、温度或功耗限制**：显存峰值 3335 / 6163 / 7795 MiB（E32 占 ~95.6%，实测两次 CUDA OOM）；系统 RAM 最低可用 8049.9 / 5357.4 / 1974.4 MiB（E32 接近耗尽）；温度峰值 90 / 91 / 90 °C；功耗峰值 93.3 / 94.2 / 124.6 W（E32 最高）。限制真实发生：E32 由显存 OOM 退出（exit_code=1）。
6. **较高 `num-envs` 是否因更新批次增大而延长迭代时间**：是。每迭代 batch = 512 / 1024 / 2048 环境步，minibatch 样本 = 32 / 64 / 128（`num-minibatches=16`）；update 均值 4.005 / 8.119 / 44.286 s——E8→E16 近线性（2.03×），E16→E32 增至 5.45×（样本仅 2×）。归因（显存压力下更新阶段分配/碎片化开销增大）为**假设，非实测结论**。

## 6. 最终推荐

选择实测最佳配置：**E16**（`--num-envs 16`）。八项结论：

- 推荐 `num-envs`：16
- 推荐 `num-steps`：64（本次基准固定口径）
- 推荐 `num-minibatches`：16（本次基准固定口径）
- 模型实际参数量：20,303,715（20.30M）
- 实测稳定 `sps`：88.095（全局环境步/s，三配置最高）
- 实测显存与 RAM 安全余量：显存峰值 6163 MiB / 8151 MiB，余量 1988 MiB（≈24.4%）；系统 RAM 最低可用 5357.4 MiB（总量 32,491.9 MiB）
- 训练 100M / 1B / 11B 步估算时长（两口径范围）：100M 连续 315–321 h（13.1–13.4 天）；1B 连续 3,153–3,206 h（131–134 天）；11B 连续 34,685–35,270 h（1,445–1,470 天）
- 证据与风险：证据 = 稳定 sps 三配置最高、正常完成（exit 0）、无 OOM、GPU 84.79%、更新阶段耗时稳定；风险 = 显存余量 24.4% 属中等，长跑碎片化/峰值波动仍有 OOM 可能，温度均值 86.2 °C（长跑降频未测得），11B 工期在本机实际不可行（约 1,470 天），E32 的崩塌说明再提高并行数在本机不可行。

吞吐量最大并非唯一标准。E32 也未带来吞吐收益（两次 OOM、非正常退出），本推荐以稳定性优先。
